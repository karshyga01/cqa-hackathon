# CQA — оценка качества диалогов

Прототип **Conversation Quality Analytics** для хакатона Freedom Broker (команда **RedLotus**).
Система загружает чаты и звонки операторов поддержки (RU / KZ / EN), оценивает работу оператора
по настраиваемому чек-листу с помощью ИИ, объясняет каждую оценку репликами-доказательствами,
поддерживает N/A, грубые ошибки, апелляции, статистику и выгрузку результатов в формате организаторов.

| | |
|---|---|
| **Модель** | `deepseek/deepseek-v4.1-flash-1017` (закреплённая версия) через OpenRouter, провайдер Together |
| **Режим** | `external_api` |
| **Цена одной оценки** | ≈ **$0,006** за чат (все вызовы, включая переспросы; замер на 65 диалогах DEV — $0,39), звонок ≈ $0,01 |
| **Скорость** | чат 10–20 с; 65 диалогов DEV ≈ 2 мин (8 параллельно) |
| **Интерфейс** | HTML, CSS, JavaScript без фреймворков — можно встроить как HTML-ресурс Dynamics 365 |
| **Сервер** | Node.js 18+, без сторонних пакетов |

## Быстрый запуск

1. Установите [Node.js](https://nodejs.org) 18 или новее. Больше ничего ставить не нужно.
2. Скопируйте `.env.example` в `.env` и впишите ключ OpenRouter:
   ```
   OPENROUTER_API_KEY=sk-or-...
   ```
   Без ключа система работает, но с **подставной оценкой** по ключевым словам (в интерфейсе помечена «подставная, не ИИ»).
3. Запустите:
   ```bash
   npm start          # http://localhost:3000
   npm test           # тесты
   ```
4. В браузере: **«Загрузить диалоги»** → код набора `DEV` → «Загрузить» → отметьте диалоги → **«Оценить выбранные»**.

Сервер слушает только `127.0.0.1`: входа по паролю нет, а в данных — переписки клиентов.

## Что умеет

**Оценка**
- Чек-лист из задания (8 критериев, веса 10/15/20/20/15/15/5, флаг грубых ошибок) создаётся при первом запуске;
  его можно менять, добавлять критерии, менять веса и типы, **заменять критерий** — каждое сохранение = новая версия.
- ИИ отвечает по каждому критерию: ответ (Да / Нет / N/A / ступень), объяснение по-русски, дословные цитаты
  с номером реплики, для «Нет» — участок, где действие ожидалось, для N/A — какое условие выполнено.
- Баллы считает **код, а не ИИ** (`frontend/js/scoring.js`): N/A с перераспределением веса, шкалы, итог из 100,
  округление «половина вверх» до двух знаков, итоги по разделам, грубые ошибки — отдельной отметкой.

**Работа с результатом**
- Карточка диалога: переписка, клик по цитате переводит к реплике, у звонков — плеер с дорожками, переход к месту записи.
- **Апелляции**: аналитик оспаривает критерий с комментарием → проверяющий видит спорную оценку, комментарий
  и фрагмент диалога → оставляет или меняет оценку с причиной → итог пересчитывается; в карточке видны
  исходная оценка, решение и финальный результат. Роль переключается в меню (входа нет — так разрешено заданием).
- **«Нужна проверка человеком»**: система сама помечает диалоги, где цитата не подтвердилась, ИИ не уверен
  или найдена грубая ошибка.
- **Вкладка «Статистика»**: где операторы теряют баллы (по критериям, из 100), распределение оценок и ответов,
  языки и каналы, все грубые ошибки с объяснениями, худшие диалоги, цена одной оценки.
- **«Выгрузить результаты»**: файл `results.json` в формате организаторов с проверкой формата.

## Контрольный этап (10 чатов, 1 час)

1. **«Загрузить диалоги»** → код контрольного набора → «Загрузить».
2. Отметьте все 10 → **«Оценить выбранные»** (≈ 1 мин).
3. **«Чек-листы»** → у нужного критерия **«Заменить»** → заполнить новый критерий → «Сохранить».
4. Снова отметьте 10 диалогов → **«Оценить выбранные»**. Заново спрашивается **только новый критерий**,
   остальные ответы берутся из прошлой оценки (отпечаток ответа не изменился) — быстро и дёшево.
5. **«Выгрузить результаты»** → набор контрольный, папка `results/prod` → «Записать в папку results».
   Окно предупредит, если какой-то диалог не оценён или оценён не по действующему чек-листу.
6. `git add results/prod/results.json && git commit -m "Контрольный набор" && git push`.

Новому критерию в `results.json` достаётся код того критерия, место которого он занял (например, `closure`).

## Выгрузка результатов (`results/dev`, `results/prod`)

Кнопка **«Выгрузить результаты»** на странице «Диалоги» (или `POST /api/results/export`).
Формат — приложение к гайду, JSON 1.0:

- одна запись на диалог, исходные `conversation_id`; коды `contact, discovery, identification, consultation,
  empathy, dialogue, closure, critical`; `true / false / null (N/A) / ступень`;
- `rationale` — объяснение ИИ (если оценку изменил проверяющий — «Изменено по апелляции: причина»);
- `evidence_turns` — номера реплик с 1 по исходному массиву (включая клиента, бота и события);
- `final_score` — итог с учётом решённых апелляций; `critical_flag` совпадает с `critical` и итог не обнуляет;
- неоценённый диалог — `status: "error"` с причиной, без нулевой оценки;
- перед записью файл проверяется: 8 критериев, допустимые значения, уникальные ID, в prod — ровно 10 записей.

`results/dev/results.json` в репозитории — оценка всех 65 диалогов DEV.

## Как устроена оценка ИИ

- **Один запрос на диалог** по всем критериям. Инструкция на английском, чек-лист на русском, цитаты на языке оригинала.
- **Строгий JSON** по схеме, построенной из чек-листа: только допустимые ответы, сначала доказательства, потом вывод.
- **Воспроизводимость**: закреплённая версия модели и провайдер без переключения, `temperature: 0`.
- **Проверка ответа кодом**: реплика существует, цитата дословно есть в реплике, у «Нет» есть участок, у N/A — условие,
  объяснение по-русски. Не прошедшие проверку критерии **переспрашиваются один раз**; не помогло — «нужна проверка человеком».
- Если модель «зациклилась» и ответ обрезан по длине — один повтор с меньшей глубиной рассуждения.
- **Повторное использование**: у каждого ответа есть отпечаток (диалог + текст критерия + общие правила + модель + версия промпта).
  Совпал — ответ берётся из прошлой оценки без запроса. Изменение веса запроса не вызывает.
- Каждая оценка дописывается в историю, старые не переписываются. Исходные транскрипты не меняются.
- Конфиденциальность: OpenRouter с `zdr: true` и `data_collection: deny`; ключ хранится только в `.env` на сервере.

### Решения по спорным местам чек-листа

Организаторы просили не угадывать их методику, а оценивать обоснованно и одинаково. Наши правила
(видны в пояснениях к критериям на странице «Чек-листы»):

| Ситуация | Решение |
|---|---|
| «Завершение»: оператор только попрощался («Пожалуйста, хорошего дня!») | **Нет** — по тексту критерия нужен итог или предложение помощи **и** прощание |
| «Завершение»: клиент ушёл или связь оборвалась раньше, чем оператор успел ответить | **N/A**; если чат закрыл сам оператор — обычная оценка |
| «Выявление потребности»: клиент сразу дал все детали (в том числе боту) | **N/A** (ответ организаторов); но если оператор переспросил уже известное — **Нет** |
| Оператор сообщил данные о счёте до подтверждения личности | **Грубая ошибка** (раскрытие конфиденциальной информации) и «Нет» по идентификации |
| Порог первой реакции 3 минуты | в оценку не входит (как и теги, вложения) |
| Звонки: приветствие не попало в запись | организаторы: N/A; в чек-листе по умолчанию N/A у «Контакта» запрещён — можно разрешить в редакторе |
| Нет базы знаний компании | правильность фактов не выдумываем, оцениваем логику и полноту ответа |

## API сервера

| Метод | Адрес | Что делает |
|---|---|---|
| GET | `/api/health`, `/api/ai` | сервер работает; подключён ли ИИ и какая модель |
| GET | `/api/datasets`, `/api/dialogs?q=`, `/api/dialogs/:key` | наборы, список, диалог (`key` = `<набор>:<id>`) |
| POST | `/api/import/preview`, `/api/import/api` | `{group_id}` — посмотреть / загрузить набор из API организаторов |
| POST | `/api/import/json`, `/api/import/text` | загрузить из файла JSON или текста |
| POST | `/api/dialogs/:key/evaluate` | `{mode: "ai"\|"mock", force?}` — оценить диалог |
| POST | `/api/evaluate` | `{keys, mode, force?}` — оценить несколько (ИИ — 8 параллельно) |
| GET | `/api/dialogs/:key/evaluation` | последняя оценка, версия чек-листа, история, апелляции |
| POST | `/api/dialogs/:key/appeals`, `/api/appeals/:id/decision` | подать апелляцию / решение проверяющего |
| GET | `/api/appeals` | очередь апелляций |
| GET, POST, PUT, DELETE | `/api/checklists…` | чек-листы и их версии |
| GET | `/api/stats?group_id=&channel=&language=` | статистика |
| GET | `/api/results?group_id=&target=` | посмотреть results.json и проверку формата |
| POST | `/api/results/export` | `{group_id, target: "dev"\|"prod", team_name}` — записать `results/<target>/results.json` |
| GET | `/api/dialogs/:key/audio…` | запись звонка (с перемоткой) |

## Настройки `.env`

| Переменная | По умолчанию | Что это |
|---|---|---|
| `OPENROUTER_API_KEY` | — | ключ OpenRouter; без него — подставная оценка |
| `OPENROUTER_MODEL` | `deepseek/deepseek-v4.1-flash-1017` | модель |
| `OPENROUTER_PROVIDER` | `together` | провайдер (без переключения на другие) |
| `OPENROUTER_REASONING` | `medium` | глубина рассуждения: low / medium / high |
| `OPENROUTER_CONCURRENCY` | `8` | сколько диалогов оценивать одновременно |
| `TEAM_NAME` | — | `team_name` для results.json (можно ввести в окне выгрузки) |
| `PORT` | `3000` | порт сайта |
| `ORG_API_URL` | адрес из задания | API организаторов без `group_id` |
| `DATA_DIR` | `data` | папка с данными |
| `ALLOWED_ORIGINS` | — | другие сайты, которым можно обращаться к API (например, Dynamics 365) |

## Ограничения

- Эталонных оценок у нас нет: правила по спорным местам — наше обоснованное решение (см. таблицу выше).
- Независимых тестов моделей на казахском нет; казахские диалоги проверены вручную на DEV.
- Звонки распознаны с ошибками (IVR на казахском, маскирование имён); чек-лист написан для чатов.
- Входа нет; сервер только для локального запуска.
